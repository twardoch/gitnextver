## Project Overview

**gitnextver** is a Git versioning automation CLI tool published to PyPI. It automatically bumps semantic version tags (`vX.Y.Z`) in Git repositories, commits all changes with the version as the commit message, creates the tag, and pushes to the remote.

### Workflow

1. Validate git repo
2. Ensure GitPython index compatibility (downgrade v3→v2 if needed)
3. Stash uncommitted changes (including untracked)
4. Pull from remote with conflict detection
5. Re-apply stash
6. Find latest `vX.Y.Z` tag, increment patch → next version
7. Stage all, commit, tag, push

## Tech Stack

- **Language:** Python 3.10+
- **Build system:** hatchling + hatch-vcs (git-tag-based semver)
- **Package manager:** uv
- **Dependencies:** GitPython, fire (CLI), rich (terminal UI), loguru (logging)

## Package Layout

## Versioning

Versions are derived from git tags via hatch-vcs. `__version__.py` is auto-generated at build time and must not be committed (it's in `.gitignore`). To release a new version, create a git tag like `v1.2.3` and build.

## Architecture Notes

- CLI via `fire.Fire(main)` — the `app()` function in `cli.py` is the entry point
- Version tags parsed with regex `^v(\d+)\.(\d+)\.(\d+)$`, only patch is auto-incremented
- Remote selection: prefers `origin`, falls back to any available remote, skips gracefully if none
- GitPython compatibility: handles index version mismatch (v3→v2 downgrade) and index.lock cleanup
- Stash/restore pattern wraps pull to avoid losing local work on conflict

## Key Design Decisions

- Defaults to `v1.0.0` when no version tags exist
- Commits use the version string as the entire commit message (e.g., `v1.0.1`)
- All files are staged (`git add -A`) — intentional for the "snapshot and tag" workflow
- Conflicts abort with user-friendly Rich panels rather than attempting auto-resolution
